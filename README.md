# Innovel Energy Services — Procurement Analytics Suite

An end-to-end procurement analytics project built during my internship at
**Innovel Energy Services Pvt Ltd**, covering six material verticals —
Electrical, Carpentry, Road Construction Materials, Solar Panels, Batteries,
and Plumbing Materials — using data extracted from **SAP Business One (SAP
B1)**, processed with **Python** and **SQL**, and visualized across 16
linked dashboards.

**➡️ Open [`dashboard/index.html`](dashboard/index.html) in a browser to explore the full linked suite**, or open any single dashboard on its own from [`dashboard/pages/`](dashboard/pages/) — see [Dashboards included](#dashboards-included) for the full list of standalone files (no install needed — see [Quick Start](#quick-start)).

> **Note on the data:** the raw internship data is confidential, so this
> repository ships a realistic, structurally-identical **synthetic** data
> dump (same SAP B1 tables, same columns, same business logic) generated by
> `scripts/generate_data.py`, so the project is fully reproducible and safe
> to publish. It simulates 12 months of activity across 60 vendors (10
> well-known India-market brands per vertical) and ~3,900 transactional
> records, rather than the 2-month internship window, so the trend
> dashboards have enough history to be meaningful — see
> [Data & Assumptions](#data--assumptions).

## Why this project

Procurement at a multi-vertical EPC/energy services company generates data
across five disconnected systems in most SME setups: requisitions, purchase
orders, goods receipts, invoices, and warehouse stock. Nobody has one place
to answer "are we overpaying for cement this quarter?" or "which vendor is
actually late most often?" without stitching together SAP exports in Excel
by hand, every time.

This project rebuilds that procure-to-pay chain as a **single semantic
layer** (SQL views over the SAP B1 tables) and a **connected dashboard
suite** on top of it, so every question above is answered live, from the
same numbers, everywhere.

## What it does

- **Ingests** SAP B1-style raw exports — Vendor Master, Material Master,
  Purchase Requisition, Purchase Order, Goods Receipt Note (GRN), A/P
  Invoice, Warehouse Inventory — for all 6 verticals.
- **Models** them into a relational SQL schema with 19 analytical views
  (one query surface per business question), so Power BI or any BI tool
  never touches raw tables directly.
- **Visualizes** the views across 16 dashboard pages (see below), built with
  Python for ETL, SQL for the semantic layer, and an interactive front end
  in place of Power BI (see [Why not a `.pbix` file](#why-not-a-power-bi-pbix-file)).
- **Quantifies impact**: a dedicated Outcomes dashboard shows a realised
  **5–7% procurement cost saving per vertical** against the material
  master's standard/benchmark rate, plus the qualitative gains (cycle-time
  visibility, vendor accountability, inventory risk reduction).
- **Updates as one**: every page reads from a single generated dataset
  (`dashboard/data.json`), so refreshing the source data refreshes every
  dashboard simultaneously — see [How "simultaneous update" works](#how-simultaneous-update-works).

## Architecture

```
SAP B1 (live DB)                 this project (offline-safe copy)
      │                                     │
      ▼                                     ▼
 raw exports  ─────────────────────►  data/*.csv   (10 SAP B1-style tables)
                                            │
                                 scripts/load_to_sqlite.py
                                            │
                                            ▼
                              sql/procurement.db (SQLite)
                              ├── 01_schema.sql   (10 tables)
                              └── 02_views.sql    (19 analytical views)
                                            │
                          scripts/build_dashboard_json.py
                                            │
                                            ▼
                              dashboard/data.json  ◄── single source of truth
                                            │
                          dashboard/index.html + app.js + style.css
                                            │
                                            ▼
                              16 linked dashboard pages
```

In production this is a **direct line from SAP B1 to Power BI**: swap
`load_to_sqlite.py`'s source from CSV files to a live SQL Server/HANA
connection, point Power BI's DirectQuery at the same 19 views, and rebuild
the 16 pages as native Power BI report pages — the SQL layer doesn't change.

## How "simultaneous update" works

Every dashboard page is a pure function of the same in-memory dataset
(`DATA`, loaded once from `data.json`). There is no per-page cache and no
manual re-entry of numbers between pages. Three things always stay in sync:

1. **Regenerate the source** — re-run `generate_data.py` (or point
   `load_to_sqlite.py` at live SAP B1 data).
2. **Rebuild the views/JSON** — re-run `load_to_sqlite.py` then
   `build_dashboard_json.py`.
3. **Refresh** — click "Refresh data" in the dashboard header (or simply
   reload the page). All 16 pages re-render from the new numbers at once.

The same pattern is exactly how a real Power BI deployment stays in sync:
one dataset, scheduled refresh, every report page bound to the same
dataset.

## Business KPIs tracked

Spend: total & monthly procurement spend · spend by category/department/project · budget utilization %
Vendor: on-time delivery % · GRN rejection % · supplier performance score · average lead time
Process: PR fulfilment % · PR→PO→GRN→Invoice cycle time · invoice overdue % · average payment delay
Inventory: stock value by warehouse · inventory aging buckets · below-reorder-level count
Impact: procurement cost savings % (5–7% band) vs. standard/benchmark rate

## Project outcomes & advantages

- **5–7% procurement cost optimization** per vertical vs. the standard/benchmark
  rate, achieved through vendor rate comparison and consolidated ordering —
  see the Outcomes dashboard for the exact figures per vertical.
- **Single source of truth** across Executive, Vendor, Inventory, and every
  process dashboard — no more reconciling different numbers between teams.
- **Cycle-time visibility** — PR→PO→GRN→Invoice delays are now visible by
  stage and by vertical instead of being discovered only when a project
  site runs short of material.
- **Objective vendor accountability** — a composite Supplier Performance
  Score replaces informal vendor reputation in review meetings.
- **Lower inventory risk** — aging and reorder-level views catch slow-moving
  and understocked material before it becomes a site stockout.
- **Reusable analytics stack** — the Python/SQL/BI pattern built for 6
  verticals here extends to new categories or business units without
  rebuilding the pipeline.

## Quick start

```bash
# 1. Clone and install dependencies
git clone <this-repo-url>
cd innovel-procurement-analytics
pip install -r requirements.txt

# 2. (Re)generate the raw SAP B1-style data dumps
cd scripts
python3 generate_data.py

# 3. Load into a local SQL database and build the analytical views
python3 load_to_sqlite.py

# 4. Build the single consolidated dashboard dataset
python3 build_dashboard_json.py

# 5. Open the dashboard
cd ../dashboard
python3 -m http.server 8000
# then open http://localhost:8000 in a browser
```

The repo already ships pre-built `data/*.csv`, `sql/procurement.db` (git-ignored,
rebuild with step 3), and `dashboard/data.json`, so you can also just open
`dashboard/index.html` directly (steps 2–4 are only needed after you change
the data).

## Tech stack

- **Python** (pandas, numpy, Faker) — synthetic data generation, ETL
- **SQL** (SQLite for this repo; portable to SQL Server / HANA) — schema +
  19 analytical views as the single semantic layer
- **HTML / CSS / JavaScript + Chart.js** — the interactive dashboard suite
- **Power BI** — the intended production front end (see below)

## Why not a Power BI `.pbix` file?

`.pbix` is a binary format that has to be authored inside Power BI Desktop
(Windows only) — it can't be generated by a script or checked into GitHub in
a reviewable way. Instead, this repo ships:

1. The **SQL views** (`sql/02_views.sql`) that a Power BI report would
   connect to directly (DirectQuery or Import mode) — this is the real
   deliverable a BI developer hands over.
2. A fully working **interactive dashboard** covering the same 16 pages, so
   anyone (including a recruiter without Power BI installed) can open
   `dashboard/index.html` in a browser and use it immediately.

If you have Power BI Desktop, you can recreate the same 16 pages in ~1–2
hours: connect to `sql/procurement.db` (via an ODBC SQLite driver) or a live
SAP B1 database, import the 19 views, and build one Power BI page per view
group listed in the [Dashboards included](#dashboards-included) table.

## Data & Assumptions

- 6 verticals × 10 established India-market brands each = 60 vendors (see
  `data/Vendor_Master.csv`).
- 60 SKUs across the 6 verticals with realistic Indian market unit prices
  (`data/Material_Master.csv`).
- 12 months of simulated transactional history (Sep 2025–Aug 2026) — wider
  than the 2-month internship window so monthly/trend dashboards have
  enough data points to be meaningful. This is a deliberate choice for
  portfolio purposes and is documented here rather than hidden.
- Cost-optimization savings are calibrated per vertical to land between 5%
  and 7% against the standard/benchmark material price — reflecting the
  actual realised outcome of the project, applied consistently across the
  synthetic data so the Outcomes dashboard is accurate to the real result.
- All company/brand names referenced as vendors are real, well-known Indian
  suppliers in their respective categories, used here only to make the
  vendor master realistic; no claim is made about an actual commercial
  relationship between Innovel Energy Services and any named brand.
